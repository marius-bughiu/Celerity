# Celerity Roadmap

This document tracks the planned direction for the Celerity project. It is a living document maintained by the project maintainers and updated as priorities shift.

Status legend: `planned`, `in-progress`, `done`, `deferred`.

## Guiding Principles

1. **Correctness first.** A "fast" collection that returns wrong answers is worthless. Every optimization must be covered by tests.
2. **Zero-cost abstractions.** Hashers are structs, generic constraints are `struct, IHashProvider<T>`, so the JIT can devirtualize and inline. This is a hard rule.
3. **Parity with BCL where it makes sense.** `TryGetValue`, `Clear`, enumeration, `IReadOnlyDictionary<TKey, TValue>` — users should be able to drop Celerity in wherever they use `Dictionary<,>`.
4. **Benchmark every perf claim.** The README's numbers are the contract. If a change regresses them, it ships only with a written justification.
5. **Document the tradeoffs.** Celerity is not "always faster." Each collection should document the workloads where it wins and where it loses.

## Vision

Celerity ships **eight** NuGet packages: the five core packages below, plus the three showcase-tier libraries in the next section. This paragraph originally described a single `Celerity.Collections` package; v2.0.0 split it into three (see milestone 2.0.0 below), the showcase tier added `Celerity.Ring` / `Celerity.Sentinel` / `Celerity.Cardinality` in v2.3.0, and `Celerity.Sorting` (v2.6.0) and `Celerity.Statistics` (v2.7.0) followed. Long-term, the project will continue to expand into a family of focused packages — each targeting a specific area where specialized, high-performance implementations can outperform the BCL in niche scenarios. The package structure mirrors the .NET ecosystem's own organization:

- `Celerity.Collections` — dictionaries, sets, and specialized collection types
- `Celerity.Hashing` — hash providers, hash evaluation utilities (positioned on *distribution quality, determinism, and zero-cost devirtualization* — not on beating `GetHashCode()` for speed; see milestone 1.6.0)
- `Celerity.Primitives` — low-level utilities that fill genuine BCL gaps: `FastMod`/`FastDiv`, struct PRNGs, span varint, integer digit-count, fast/compliant GUID, alignment/bit-packing (see milestone 2.1.0; we deliberately do not reimplement what `BitOperations`/`TensorPrimitives` already inline)
- `Celerity.Sorting` — non-comparison sorts and selection over primitive keys: `RadixSort`, `CountingSort`, `PartialSort` (see the rolling post-roadmap lane below; the BCL's `Array.Sort` is a scalar comparison introsort and is contractually in-place, so it cannot host a radix path at all)
- `Celerity.Statistics` — streaming summary statistics in bounded memory: `DDSketch`, `ReservoirSampler`, `RunningStatistics` (see the rolling post-roadmap lane below; `System.Linq` has `Average` and stops, so there is no quantile type, no sampler and no higher moment to be a counterpart to)

Each package will remain narrowly scoped: if a type doesn't offer a measurable performance advantage over its BCL counterpart in at least one documented workload, it doesn't ship.

### The "Built with Celerity" showcase tier

Alongside the core packages, a separate **showcase tier** ships standalone libraries *built on* Celerity, each filling a niche where a pure-managed .NET implementation beats dropping to native code. These are downstream consumers, not core packages: they demonstrate the core in a real problem domain and are held to their own domain bar rather than to the core's "must beat the BCL counterpart" rule (in most cases the BCL has no counterpart at all).

All three shipped together in **v2.3.0** (2026-07-19) and are rostered under [that milestone](#the-showcase-tier--ring-sentinel-cardinality) below; what follows is the tier's standing description, not a plan.

- `Celerity.Ring` — deterministic consistent-hash and rendezvous (HRW) rings for sharding and request routing, producing byte-identical node assignment across OS / architecture / runtime. Status: `done` — shipped in v2.3.0.
- `Celerity.Sentinel` — streaming abuse / heavy-hitter detection (top offenders, per-key rate, fan-out cardinality) in a fixed footprint regardless of key cardinality. Status: `done` — shipped in v2.3.0.
- `Celerity.Cardinality` — mergeable approximate `COUNT(DISTINCT)` and windowed dedup over unbounded managed streams, with deterministic cross-shard merge. Status: `done` — shipped in v2.3.0.

Cross-process sketch wire-serialization is deliberately deferred — it needs core Celerity to expose sketch bytes first, and the core is explicitly [not a serialization library](#non-goals).

Status: `done` — `FrozenCelerityDictionary<TValue>` / `<TValue, THasher>` search for a collision-free single-probe layout at construction and fall back to linear probing when the chosen hasher collides two keys' raw codes, so lookups are always correct. Status: `done`. Tracked in [#22](https://github.com/marius-bughiu/Celerity/issues/22).
- `CelerityMultiMap<TKey, TValue, THasher>` — multi-value dictionary. Status: `done` — a one-to-many map that reuses `CelerityDictionary`'s open-addressed key table and stores a `List<TValue?>` value group per key; `Add` appends rather than overwrites, `Remove(key, value)` / `RemoveAll(key)` are the two removal shapes, the indexer returns an empty group for an absent key, and the type implements `ILookup<TKey, TValue?>`. Tracked in [#18](https://github.com/marius-bughiu/Celerity/issues/18).
- `CelerityMultiSet<T, THasher>` — counting multiset (bag/counter), the element→count sibling that completes the `CelerityMultiMap` one-to-many family. Status: `done` — reuses `CelerityDictionary`'s open-addressed table with a parallel `int[]` multiplicity per element; `Add` / `Add(count)` are single-probe increments (vs the two-probe `Dictionary<T,int>` `GetValueOrDefault` idiom — the documented BCL-beating frequency-counting workload), `Remove` / `RemoveAll` / `SetCount` manage multiplicities, `Count` is distinct elements and `TotalCount` the sum of occurrences, and it enumerates `(element, count)` pairs. Filed and shipped after the roadmap was otherwise exhausted (a tier-(c) enhancement). Tracked in [#235](https://github.com/marius-bughiu/Celerity/issues/235).
- `SmallDictionary<TKey, TValue>` — flat-array implementation optimized for `n <= ~16`. Status: `done` — `SmallDictionary<TKey, TValue>` linear-scans insertion-dense parallel arrays with `EqualityComparer<TKey>.Default` (no hasher, so the default key is stored inline rather than out-of-band), trading `O(1)` for `O(n)` to win at small `n`; it implements `IReadOnlyDictionary<TKey, TValue?>` with the full dictionary surface. Tracked in [#61](https://github.com/marius-bughiu/Celerity/issues/61).

## Milestone 1.6.0 — Hasher performance audit & honest positioning

A correctness-of-claims pass on the hashing layer, prompted by the observation that **the hashers are not necessarily faster than `GetHashCode()`** — and, for `int` keys, *cannot* be (`int.GetHashCode()` is identity, i.e. zero work). The real value of the struct hashers is **distribution quality (avalanche), determinism, adversarial resistance, and the zero-cost devirtualized generic** — not raw hashing speed. This milestone makes the benchmarks and the docs tell that honest story. It ships in the current single package, before the 2.0.0 restructure.

- Benchmark hashers **end-to-end through the dictionaries** (insert/lookup across uniform / sequential / clustered / adversarial key distributions), reporting collision rate and avg/max probe length — not just an isolated `Hash()` loop. The clustered/adversarial cases are where a strong hasher wins end-to-end even though it "loses" the isolated microbench. Status: `done` — `HasherEndToEndBenchmark` (extended suite) times every integer hasher through `IntDictionary` for insert + lookup across all four key shapes vs the BCL `Dictionary`, and the new public `ProbeStatisticsEvaluator` / `ProbeStatistics` ([`docs/api/hashing.md`](docs/api/hashing.md#end-to-end-probe-analysis)) replays the real open-addressed linear-probing placement to report average / worst-case probe length and the open-addressing collision rate (surfaced as a deterministic `--probe-analysis` markdown report and a measured table in [`docs/performance.md`](docs/performance.md#measure-probe-length-not-just-hash-speed)). The numbers show the cheap hashers winning on uniform/sequential keys and the naive fold collapsing on clustered/adversarial keys while the Wang/Murmur3 finalizers hold near a 1.75 average probe. Tracked in [#182](https://github.com/marius-bughiu/Celerity/issues/182).
- Make the isolated microbenchmarks honest: consume results (the identity `int` hash is otherwise dead-code-eliminated), add an `EqualityComparer<T>.Default` baseline (the realistic thing a dev replaces), and label identity/`GetHashCode()` as the **zero-work floor** no mixing hasher can beat. Status: `done` — every hasher microbenchmark already XOR-folds its codes into a returned value (BDN consumes it, so no DCE), and both `IntegerHasherBenchmark` (`{Type}_EqualityComparer` per `int`/`long`/`uint`/`ulong`/`Guid`) and `StringHasherBenchmark` (`EqualityComparer_Default`) now carry an `EqualityComparer<T>.Default.GetHashCode()` baseline arm alongside the direct `GetHashCode()` one — the per-probe call a BCL `Dictionary<,>` actually makes. The class remarks label the microbenchmarks a raw-mixing-cost diagnostic and the `int`/`long` identity/`_Bcl` rows the zero-work floor; the new arms auto-render on the gh-pages **Hash function throughput** dashboard. Tracked in [#183](https://github.com/marius-bughiu/Celerity/issues/183).
- Reposition the hasher docs/README away from "faster hashing" toward distribution/avalanche/determinism, with an honest "choosing a hasher" guide (the speed-vs-quality curve, the F14/ahash/FxHash framing, the Marvin32 string-determinism tradeoff, and the caveat that **fixed-seed hashers are not a HashDoS defence**). Status: `done` — `README.md` reframes the "up to 2.4× faster" headline as a *collection-layout* win independent of the hasher, and both `README.md` and `docs/api/hashing.md` lead with distribution/determinism and carry an explicit HashDoS caveat (fixed-seed hashers are not a flooding defence; what stops flooding is a keyed PRF with a secret, per-process-random key, so BCL Marvin32 is the safe default for untrusted string keys). `hashing.md`'s "Choosing a hasher" section gains a speed-vs-quality-curve framing block, and the benchmark docs across `hashing.md` / `docs/performance.md` reframe the isolated `Hash()` sweeps as a raw-mixing-cost diagnostic. Tracked in [#184](https://github.com/marius-bughiu/Celerity/issues/184).
- Add explicit identity/passthrough integer hashers (`Int32IdentityHasher` / `Int64IdentityHasher`) as the zero-work floor, and document the rule: uniform/trusted keys → skip mixing; clustered/adversarial keys → mix. Status: `done` — `Int32IdentityHasher` (`Hash(key) => key`) and `Int64IdentityHasher` (`Hash(key) => (int)key`) ship as the labelled floor of the integer hasher ladder (no mixing hasher beats identity on speed; the value of the struct hashers is distribution/determinism, not hashing speed), are exercised as `*_Identity` rows in `IntegerHasherBenchmark`, and carry the skip-vs-mix decision rule plus the open-addressed-table-sensitivity and not-a-HashDoS-defence caveats in `docs/api/hashing.md` and the README. Library defaults are unchanged (identity is opt-in). Tracked in [#185](https://github.com/marius-bughiu/Celerity/issues/185).

The *new collections* and *infrastructure* work below has shipped, the **package restructure itself — the defining work of this milestone — has landed** (the library builds and packs as three packages, each multi-targeting `net8.0;net9.0;net10.0`, #189), and the **release pipeline is now complete** (symbol packages, SourceLink, deterministic builds, and a publish-time package-validation gate, #190). **`v2.0.0` shipped on 2026-06-21**, closing the human-gated release review ([#213](https://github.com/marius-bughiu/Celerity/issues/213)); the milestone is complete and closed.

### New collections

- Specialized collections for domain-specific workloads (e.g. graph traversal, spatial indexing). Status: `done` — four specialized types shipped and [#30](https://github.com/marius-bughiu/Celerity/issues/30) was closed as substantially complete (the two remaining checklist entries, `StringDictionary` and `StructDictionary`, were descoped as redundant with `CelerityDictionary`'s existing string-hasher surface and zero-boxing struct-key support — per the guiding rule, a type that doesn't beat the BCL on a documented workload doesn't ship). `BloomFilter<T, THasher>` is a probabilistic membership filter with bit-array storage, no false negatives, and a tunable false-positive rate, sizing `m` / `k` from the expected element count and deriving its `k` bit probes from a single `IHashProvider<T>` call by double hashing. `BitSet` is its exact, deterministic counterpart: a dense fixed-length bit vector packed into 64-bit words with `O(n/64)` hardware-popcount cardinality (`Count`) and SIMD-accelerated bulk `And` / `Or` / `Xor` / `Not`, a faster, count-aware alternative to `System.Collections.BitArray`. `HyperLogLog<T, THasher>` is the probabilistic cardinality estimator: it counts the number of *distinct* elements in a stream of any size from a fixed array of `2^precision` one-byte registers (16&#160;KB by default) with a ~0.8% relative standard error and no growth with the data, derives its 64-bit hash from a single `IHashProvider<T>` call by SplitMix64 avalanche, applies linear counting for small cardinalities, and merges equal-precision estimators with `UnionWith` for distributed counting. `CountMinSketch<T, THasher>` completes the streaming-sketch trio (membership → cardinality → frequency): it estimates *how many times* each element occurs from a fixed `depth × width` grid of counters sized from an `epsilon` / `delta` error budget, **never underestimates** (overestimates bounded by `epsilon · TotalCount` with confidence `1 − delta`), derives its `depth` counter columns from a single `IHashProvider<T>` call by double hashing, and merges equally-sized sketches with `UnionWith` for distributed heavy-hitter / frequency counting. Tracked in [#30](https://github.com/marius-bughiu/Celerity/issues/30) (closed). `CuckooFilter<T, THasher>` later extended the family with **deletable** membership ([#223](https://github.com/marius-bughiu/Celerity/issues/223)): the same no-false-negatives / tunable-false-positive contract as `BloomFilter` but backed by partial-key cuckoo hashing (power-of-two fingerprint buckets, `i2 = i1 XOR h(fingerprint)`, eviction with a single-entry victim cache), so it supports `Remove` with ≤2-bucket lookups — the membership filter for a set that shrinks as well as grows. Status: `done`. `TopKSketch<T, THasher>` later completed the streaming-sketch family's fourth axis — **top-k / heavy hitters** ([#238](https://github.com/marius-bughiu/Celerity/issues/238)): the Space-Saving algorithm (Metwally et al. 2005) reports a high-cardinality stream's most frequent elements from a fixed `k` monitors (an indexed min-heap keyed on count, with the element→monitor index dogfooding `CelerityDictionary`), in `O(k)` memory rather than the `O(distinct)` a `Dictionary<T,int>` frequency table needs to rank the top few; it never underestimates a monitored count and never misses an element above `TotalCount / k`. Add-and-query only, with no `UnionWith` (bounded top-k summaries have no exact merge). Filed and shipped after the roadmap was otherwise exhausted (a tier-(c) enhancement). Status: `done`.
- Memory-pooled collections for zero-allocation hot paths. Status: `done` — `PooledCelerityDictionary<TKey, TValue, THasher>` is a drop-in, `IDisposable` peer of `CelerityDictionary` whose backing key/value arrays are rented from `ArrayPool<T>.Shared` and returned on `Dispose` (and on every internal resize), recycling buffers across build/use/dispose cycles to cut Gen 0 / LOH pressure on hot paths that rebuild dictionaries frequently. It tracks its logical power-of-two capacity independently of the (possibly over-provisioned) rented array length, clears reference-type buffers on return to prevent leaks, and throws `ObjectDisposedException` after disposal. Tracked in [#21](https://github.com/marius-bughiu/Celerity/issues/21).
- SIMD-accelerated probing (SSE2/AVX2) similar to Swiss Tables / `F14`. Status: `done` — shipped as a new opt-in collection type, `SwissDictionary<TKey, TValue, THasher>`, a drop-in peer of `CelerityDictionary` that keeps a parallel one-byte control-tag array so a single portable `Vector128` compare tests a whole 16-slot group per probe, filtering candidates by a 7-bit hash fragment before any key comparison; deletion uses tombstones reclaimed by an occasional rehash. The default is unchanged — this is an additional type for lookup-heavy workloads (large tables, many negative lookups, clustered keys), at the cost of one control byte per slot. Tracked in [#64](https://github.com/marius-bughiu/Celerity/issues/64).
- Struct-of-arrays layout experiment for cache-friendly memory access. Status: `done` — shipped as a new opt-in collection type, `HashCachingDictionary<TKey, TValue, THasher>`, a drop-in peer of `CelerityDictionary` that keeps a dense side array of 32-bit hash fingerprints alongside the parallel key/value arrays. ## Milestone 2.1.0 — Celerity.Primitives: fast math & low-level utilities

The "fast-utils" expansion that fills `Celerity.Primitives` with specialized BCL alternatives. Comprehensive research against the current .NET (8/9/10) surface shows the BCL has closed most classic gaps — `System.Numerics.BitOperations`, `System.Numerics.Tensors.TensorPrimitives`, `Convert.ToHexString`, `System.Buffers.Text.Base64`, and generic-math `Math` already inline to optimal/SIMD code. So this milestone ships only the **defensible white space**, each with a documented BCL-beating workload (the hard rule), and deliberately **does not** reinvent what the BCL already does well.

### Ship — real gaps with a documented workload

- `FastMod` / `FastDiv` — Lemire reciprocal modulo & division by a runtime-constant divisor (the BCL's `HashHelpers.FastMod` is `internal`-only); 2–4× over `%`/`/` for repeated mod by the same divisor (hash buckets, ring buffers, sharding). Status: `done` — shipped on `FastUtils` with 32-bit (`uint` → `ulong` multiplier) and 64-bit (`ulong` → `UInt128` multiplier) overloads: `GetFastModMultiplier` precomputes the `ceil(2^W / d)` reciprocal once, then `FastMod` / `FastDiv` reduce each operation to a widening multiply + shift. `FastMod` is exact for every value and `divisor >= 1`; `FastDiv` for `divisor >= 2` (the `divisor == 1` multiplier overflows to 0 — a documented call-site guard). Correctness is fuzzed against `%` / `/` across both widths (representative + extreme divisors, boundary + random + exhaustive-low-range dividends), benchmarked vs the hardware operators in the extended-suite `FastModBenchmark`, documented in [`docs/api/utilities.md`](docs/api/utilities.md#fastmod--fastdiv) and the README, and exercised by the Native AOT smoke test. Tracked in [#191](https://github.com/marius-bughiu/Celerity/issues/191).
- Struct PRNG suite — value-type, allocation-free, inlinable, seed-deterministic xoshiro256\*\* / xoroshiro128+ / SplitMix64 (+wyrand/PCG). `System.Random` is a heap class behind virtual dispatch and its **seeded** path falls back to the legacy Knuth algorithm. Curated, no marginal variants. Status: `done` — `Celerity.Primitives.SplitMix64` / `Xoshiro256StarStar` / `Xoroshiro128Plus` / `WyRand` / `Pcg32` ship as mutable `struct`s implementing a one-method `IRandomSource` (`ulong NextUInt64()`); the shared `NextUInt32` / `NextDouble` / `NextSingle` / `NextBool` / bounded-and-unbiased (Lemire) `NextInt` / `NextInt64` / `NextBytes` surface is built once over the interface as `ref this` extension methods constrained to `where TRng : struct, IRandomSource`, so it devirtualizes, inlines, and runs zero-cost over any generator (e.g. a generic Fisher–Yates shuffle). Every constructor is explicitly seeded and deterministic; the multi-word generators expand the seed through `SplitMix64` so every seed (including `0`) is valid. Cross-checked against independent reimplementations and the published SplitMix64 seed-0 vector, covered family-wide by `RandomSourceContractTests`, benchmarked vs seeded/shared `System.Random` in the extended-suite `PrngBenchmark`, documented in [`docs/api/utilities.md`](docs/api/utilities.md#struct-prngs) and the README, and exercised by the Native AOT smoke test. Tracked in [#192](https://github.com/marius-bughiu/Celerity/issues/192).
- Span-based varint codec — LEB128 + zig-zag `Try(Write|Read)` over spans (the BCL's 7-bit-encoded int is only on `BinaryReader`/`BinaryWriter`, stream-bound and allocating). Status: `done` — `Celerity.Primitives.VarInt` ships `TryWriteVarInt` / `TryReadVarInt` over `Span<byte>` / `ReadOnlySpan<byte>` for `uint` / `ulong` (LEB128) and `int` / `long` (zig-zag + LEB128), plus a `VarIntLength` size helper, the `MaxVarIntLength32` / `MaxVarIntLength64` buffer-sizing ceilings, and standalone `ZigZagEncode` / `ZigZagDecode` transforms. Every `Try*` is bounds-safe (returns `false` with `0` bytes on a short / truncated / over-length / overflowing buffer, never throws). Round-trip-fuzzed (per-width boundaries + extremes + dense exhaustive low-range sweeps), benchmarked vs `BinaryWriter.Write7BitEncodedInt64` in the extended-suite `VarIntBenchmark`, documented in [`docs/api/utilities.md`](docs/api/utilities.md#varint-span-varint-codec) and the README, and exercised by the Native AOT smoke test. Tracked in [#193](https://github.com/marius-bughiu/Celerity/issues/193).
- Integer digit-count / `Log10` — public `CountDigits` (the BCL's LZCNT-based one is `internal`); for buffer sizing and column alignment. Status: `done` — `FastUtils.CountDigits` ships `uint` / `ulong` (exact, branch-lean: the 32-bit path is Lemire's single-`Log2`/LZCNT-plus-magic-table count, the 64-bit path a one-division comparison ladder) plus signed `int` / `long` overloads that count the magnitude (sign excluded, `MinValue` handled without overflow), and the companion integer `Log10(uint)` / `Log10(ulong)` (`CountDigits - 1`, exact at every power of ten where the floating-point `Math.Log10` mis-rounds; `Log10(0)` returns `0`). Correctness is reconciled against `value.ToString().Length` (two dense exhaustive `[0, 2,000,000)` sweeps + every power-of-ten boundary + ~200k random per width), benchmarked vs a naive divide-by-ten loop and `(int)Math.Log10 + 1` in the extended-suite `CountDigitsBenchmark`, documented in [`docs/api/utilities.md`](docs/api/utilities.md#countdigits--log10-base-10-digit-count) and the README, and exercised by the Native AOT smoke test. Tracked in [#194](https://github.com/marius-bughiu/Celerity/issues/194).
- Fast non-crypto GUID v4 (from the struct PRNG) + RFC-9562 big-endian v7 (sortable, DB-friendly; the BCL's `CreateVersion7` uses a non-big-endian layout that bloats DB indexes). Status: `done` — `FastGuid.CreateVersion4<TRng>(ref TRng)` is a non-cryptographic random v4 filled from any `IRandomSource` struct PRNG, and `FastGuid.CreateVersion7<TRng>(ref TRng, long unixTimeMilliseconds)` is an RFC 9562 v7 whose 48-bit timestamp sits in the **big-endian** most-significant bytes so the canonical string sorts in creation order (unlike .NET 9's mixed-endian `Guid.CreateVersion7`, which scrambles the DB sort order); the `Guid` is built via the field constructor with big-endian reads so this needs no .NET 9-only API (the library targets net8.0). `GuidV7Generator<TRng>` adds a strictly monotonic v7 sequence (RFC 9562 monotonic-counter method: a 12-bit `rand_a` counter that advances within a millisecond and borrows from the next on overflow), so a same-millisecond burst is still strictly increasing. Both set the correct version/variant bits, are deterministic from a seeded generator, and are documented prominently as **NOT cryptographically secure** (use `Guid.NewGuid()` for unguessable IDs). Benchmarked vs `Guid.NewGuid()` (and `Guid.CreateVersion7` under `#if NET9_0_OR_GREATER`) in the extended-suite `GuidBenchmark`, documented in [`docs/api/utilities.md`](docs/api/utilities.md#fastguid-fast-non-crypto-guid-v4--v7) and the README, and exercised by the Native AOT smoke test. Tracked in [#195](https://github.com/marius-bughiu/Celerity/issues/195).
- Alignment helpers + span bit-packing over caller-owned memory (`AlignUp`/`AlignDown`/`IsAligned`, span bit get/set/scan/popcount), distinct from the owning `BitSet` collection. Status: `done` — `FastUtils.AlignUp` / `AlignDown` / `IsAligned` ship power-of-two alignment for `int` / `long` sizes and pointer-sized `nuint` addresses (the `internal` BCL `Align` trick, exposed and `BitOperations.IsPow2`-validated), and `Celerity.Primitives.SpanBits` is the **non-owning** counterpart to `BitSet`: `Get` / `Set` / `Clear` / `Flip` / hardware-`POPCNT` `PopCount` / `TZCNT` `NextSetBit` scan over a caller-owned `Span<ulong>` (a `stackalloc` buffer, a slice, a pooled array), plus a `WordCount` sizing helper — where `BitSet` owns its storage, `SpanBits` operates on memory you already manage. Reconciled against a modulo oracle (alignment) and a `bool[]` model (bits), benchmarked vs `System.Collections.BitArray` in the extended-suite `SpanBitsBenchmark`, documented in [`docs/api/utilities.md`](docs/api/utilities.md#alignment-helpers-alignup--aligndown--isaligned) and the README, and exercised by the Native AOT smoke test. Tracked in [#196](https://github.com/marius-bughiu/Celerity/issues/196).
- Sequential bit-field cursors over caller-owned spans — `BitWriter` / `BitReader`. Status: `done` — a bounds-safe pair of `ref struct` cursors for packing and unpacking arbitrary-width bit fields over a `Span<byte>` / `ReadOnlySpan<byte>`, with no stream and no allocation, filling the gap between byte-granular `VarInt` and random-access `SpanBits`: a record of odd-width fields occupies exactly `ceil(total_bits / 8)` bytes instead of one byte per field (wire protocols, compression bitstreams, packed columnar / bitmap-index encodings). Bit order is LSB-first (the DEFLATE convention); the BCL has no span-based multi-bit bit writer. Released in **v2.3.0** and rostered here retroactively by the 2026-Q3 roadmap review — it landed after this milestone was otherwise complete, but belongs to the `SpanBits` / `VarInt` line above rather than to the collection work it shipped alongside.

### Research — verify the win before shipping

- Fused/specialized SIMD reductions **not** covered by `TensorPrimitives` (simultaneous min+max, integer histogram, overflow-checked sum) — spike, ship only the winners. Status: `done` — shipped as `Celerity.Primitives.SimdReductions` with the two candidates that beat the BCL composition on a documented workload: **`MinMax`** (`int`/`long`/`uint`/`ulong`) folds two running `Vector<T>` accumulators in a **single pass** vs the two-pass `TensorPrimitives.Min` + `TensorPrimitives.Max`, measuring **~1.8× faster on a large out-of-cache span** (a memory-bandwidth win; a wash in-cache, documented), and **`CheckedSum`** (`int`) widens each lane to `long` so the SIMD accumulation cannot overflow and throws `OverflowException` rather than wrapping like `TensorPrimitives.Sum`, measuring **~4.6× faster than the only safe alternative (a scalar `checked` loop)**. The third candidate, an integer **histogram / bincount**, was evaluated and **not shipped** — its only BCL alternative is LINQ `GroupBy().Count()`, the win is purely allocation avoidance achievable with a one-line `counts[v]++` loop, and the scatter pattern does not vectorize portably. See [`docs/api/utilities.md`](docs/api/utilities.md#simdreductions-fused--specialized-simd-reductions). Tracked in [#197](https://github.com/marius-bughiu/Celerity/issues/197).
- Guaranteed-branchless conditional `Select` — verify the JIT actually branches (it already emits `cmov` for `Math.Min`/`Max`/`Abs`/`Clamp`) before shipping. Status: `done` — the spike confirmed the JIT does **not** reliably if-convert a general data-dependent `condition ? a : b`: a per-element blend over a 1,000,000-element span with a 50/50 **unpredictable** condition runs ~6× faster branch-free (~0.5 ms vs ~3.0 ms), the textbook misprediction signature. Shipped as `Celerity.Primitives.Branchless.Select` — scalar overloads for `int`/`long`/`uint`/`ulong`/`float`/`double` (floats bit-exact via integer-bit reinterpret) plus bulk per-element span blends (`int`/`long`/`float`/`double`) that auto-vectorize, all via the mask trick `whenFalse ^ ((whenTrue ^ whenFalse) & mask)`. The recognised `cmov` idioms (`Math.Min`/`Max`/`Abs`/`Clamp`) are deliberately **not** re-shipped, and the docs/benchmark flag that the win is specific to the unpredictable-condition case (a well-predicted branch is free). See [`docs/api/utilities.md`](docs/api/utilities.md#branchless-guaranteed-branch-free-conditional-select). Tracked in [#198](https://github.com/marius-bughiu/Celerity/issues/198).

### Explicitly out of scope — the BCL already does these well

Per the guiding rule, these are **not** worth shipping because they already inline to optimal/SIMD code: next-power-of-two / `IsPow2` / `Log2` / `PopCount` / `LeadingZeroCount` / `TrailingZeroCount` / `RotateLeft`/`Right` (`System.Numerics.BitOperations`); SIMD `Sum`/`Min`/`Max`/`Dot`/`IndexOf`/`Contains` (`TensorPrimitives`, generic over `INumber<T>`, + `MemoryExtensions`/`SearchValues`); hex and Base64 encode/decode (`Convert.ToHexString`, `System.Buffers.Text.Base64`, AVX-512); byte-swap/endianness (`BinaryPrimitives`); branchless `Min`/`Max`/`Abs`/`Clamp` (JIT `cmov`); and generic xxHash/CRC span hashing (`System.IO.Hashing` — depend on it rather than reimplement).

## Milestone 2.3.0 — specialized-collection expansion (shipped 2026-07-19)

**Rostered retroactively by the 2026-Q3 roadmap review.** The planned roadmap was complete through 2.1.0, but development did not stop — it continued under the convention this project had already been following informally: *when the plan is exhausted, the next item comes from reading the source*, either a BCL-parity gap or a family whose members are not symmetric. That produced a full release worth of collections that were never on the roadmap. This section records them so the roadmap stays a faithful account of what shipped, not only of what was planned.

### Dictionary → set parity (the specialized-set family)

The dictionary family had four specialized performance peers while the set family had none. Closing that asymmetry produced four types, each a drop-in peer of `CeleritySet` differing only in probing/storage strategy. All `done`.

- `RobinHoodSet<T, THasher>` — Robin Hood open addressing; bounds probe-length variance on clustered / adversarial elements, negative lookups exit early.
- `HashCachingSet<T, THasher>` — parallel cached hash fingerprints; a probe compares one integer before dereferencing an element, winning on lookup-dominated sets and costly-equality elements.
- `PooledCeleritySet<T, THasher>` — `ArrayPool`-backed and `IDisposable`; recycles buffers for short-lived, frequently-rebuilt sets instead of generating Gen 0 / LOH garbage.
- `SmallSet<T>` — flat-array linear scan for `n <= ~16`, the set counterpart of `SmallDictionary` and the last dictionary→set parity gap.

Their differential fuzz targets landed with them ([#252](https://github.com/marius-bughiu/Celerity/issues/252)), closing a harness gap where the newest sets were not driven against a BCL oracle.

### Enum-keyed collections

- `EnumSet<TEnum>` — bit-vector set for enum element types (the .NET analogue of Java's `EnumSet`); membership is a single bit test and set algebra is word-wise. Status: `done`. Tracked in [#259](https://github.com/marius-bughiu/Celerity/issues/259).
- `EnumMap<TEnum, TValue>` — dense array-backed dictionary for enum keys, the dictionary counterpart of `EnumSet`; a lookup is a direct array index, not a hash probe. Status: `done`. Tracked in [#263](https://github.com/marius-bughiu/Celerity/issues/263).

Both support enums whose members are small non-negative integers; a negative or sparse (`[Flags]`) enum throws at construction. Note: these are enum-generic, so they cannot join the `int`-parameterized shared test suites — they carry dedicated coverage instead.

### BCL gaps — structures .NET does not ship at all

Each of these fills a genuine hole in the framework rather than beating an existing BCL type.

- `Deque<T>` — growable double-ended queue over a circular buffer. .NET has no array-backed deque (`Queue<T>` / `Stack<T>` are single-ended; `LinkedList<T>` allocates per element). All four end operations plus a front-relative indexer are `O(1)` amortized. Status: `done`. Tracked in [#268](https://github.com/marius-bughiu/Celerity/issues/268).
- `DisjointSet<T>` — union-find with union-by-size and path halving. .NET ships no union-find; the idiomatic `Dictionary<T, HashSet<T>>` merge is quadratic where this is near-linear. Status: `done`. Tracked in [#272](https://github.com/marius-bughiu/Celerity/issues/272).
- `LruCache<TKey, TValue, THasher>` — fixed-capacity LRU. .NET ships no bounded LRU cache; the steady-state get/put/evict path allocates nothing, unlike the idiomatic `Dictionary` + `LinkedList` hand-roll. Status: `done`. Tracked in [#266](https://github.com/marius-bughiu/Celerity/issues/266).
- `IndexedPriorityQueue<TElement, TPriority, THasher>` — an *addressable* binary heap: unlike `PriorityQueue<,>` it supports decrease-key / update-priority and remove-by-element in `O(log n)`, the operation Dijkstra / A\* / event simulation need and the BCL type cannot do without a lazy-deletion workaround. Status: `done`.

### Membership filters

- `XorFilter<T, THasher>` — build-once, immutable membership filter; smaller (~9.84 bits/element) and faster to query (three probes, no probe loop) than `BloomFilter` or `CuckooFilter` at the same false-positive rate, completing the membership-filter family with its static member. Status: `done`.

### Primitives

- `BitWriter` / `BitReader` also shipped in this release; they are rostered under milestone 2.1.0 above, alongside the `SpanBits` / `VarInt` work they extend.

### The showcase tier — Ring, Sentinel, Cardinality

The rest of this release, and the part that is not a collection at all: three standalone packages built *on* `Celerity.Collections` rather than inside it, described in [the Vision section](#the-built-with-celerity-showcase-tier) above. They are downstream consumers held to their own domain bar, not core packages held to the "must beat the BCL counterpart" rule — in each case the BCL has no counterpart at all. All `done`, all shipped in v2.3.0.

- `Celerity.Ring` — consistent-hash and rendezvous (HRW) rings whose node assignment is byte-identical across OS, architecture and runtime, so every node in a cluster resolves a key to the same shard.
- `Celerity.Sentinel` — streaming abuse / heavy-hitter detection (top offenders, per-key rate, fan-out cardinality) in a footprint that does not grow with key cardinality, so attacker key-rotation cannot drive it to unbounded memory the way a `Dictionary<,>` counter is driven.
- `Celerity.Cardinality` — mergeable approximate `COUNT(DISTINCT)` and windowed dedup over unbounded streams, with a cross-shard merge that is deterministic on every runtime.

None of the three carries a tracking issue: they were built under the same source-reading convention as the collections above, before the rolling post-roadmap lane below existed to file them against. Cross-process sketch wire-serialization remains deferred, for the reason given in the Vision section.

## Rolling post-roadmap work — the standing lane

The planned roadmap is complete through 2.1.0, and every release since has been driven entirely by source-reading rather than by the plan. Rather than let that work keep landing unrostered — the drift the 2026-Q3 review was opened to catch — this is a **standing lane** that new post-roadmap work is filed against as it is identified. It is not a fixed scope with a completion date; it is the home for the tier-(c) work.

Work admitted here is held to exactly the same bar as everything above: the hard rule (a documented workload where it beats its BCL counterpart, or a genuine BCL gap) and the [non-goals](#non-goals).

**On the milestone number.** This lane was opened as a GitHub milestone called `2.4.0`, which is the number the issues below still carry. The number was always a misnomer: a standing lane is not a release scope, and this one went on to span four shipped releases (v2.4.0 through v2.7.0), so a `2.4.0` label never said which release an issue shipped in — the `Status:` line and `CHANGELOG.md` say that. The 2026-Q3 review closed that milestone at 100% (32 issues, 0 open) and the lane now carries a milestone named **[Rolling post-roadmap work](https://github.com/marius-bughiu/Celerity/milestone/8)**, which cannot be mistaken for a version.

### Shipped in v2.4.0 (2026-07-26)

The three collections the lane opened with, released together. Other lane work shipped in the same tag — the `IHashProvider64<T>` entropy fix among it — and is rostered under its own theme below.

- `Trie<TValue>` — ordered prefix tree mapping `string` keys to values; the operation no hash table can do is *prefix* enumeration in sorted order without scanning every key. Status: `done` — released in v2.4.0. Tracked in [#285](https://github.com/marius-bughiu/Celerity/issues/285).
- `SparseSet` — bounded-universe `[0, Universe)` integer set with `O(1)` clear and dense iteration; the classic ECS / graph-visited-set structure, where `HashSet<int>.Clear()` and hash iteration both lose. Status: `done` — released in v2.4.0. Tracked in [#287](https://github.com/marius-bughiu/Celerity/issues/287).
- `FenwickTree<T>` — Binary Indexed Tree over a fixed-length sequence: `O(log n)` point update *and* prefix-sum query, where a running-sum array gives `O(1)` query but `O(n)` update and a plain array gives the reverse. Status: `done` — released in v2.4.0. Tracked in [#289](https://github.com/marius-bughiu/Celerity/issues/289).

### Planned

The 2026-Q3 review surveyed the shipped surface against the current .NET 8/9/10 BCL and adversarially verified each candidate against the hard rule and the [non-goals](#non-goals). Thirty-six candidates were proposed; twelve were rostered, in four themes. The lane's issues carry the detail; all twelve have since closed.

**Drop-in parity and correctness in the shipped surface.** Work on code already on NuGet, and the highest-confidence group.

- Fix `HyperLogLog`'s hash-entropy floor. `Hash64` widened a 32-bit `IHashProvider<T>` result, so the reachable hash space was 2^32 — while the type's own docs asserted a 64-bit space and skipped the classical large-range correction on that basis. The bias exceeded the advertised 0.81% standard error from ~1e8 distinct elements, in exactly the regime the type is sold for. Status: `done` — `IHashProvider64<T>` (`ulong Hash64(T key)`) ships as a standalone sibling interface in `Celerity.Hashing`, deliberately *not* deriving from `IHashProvider<T>` so the two contracts stay independent and a 64-bit hasher is never forced to publish a lossy 32-bit fold. Fourteen built-in hashers implement it — `Int64WangHasher`, `Int64Murmur3Hasher`, `UInt64WangHasher`, `UInt64Murmur3Hasher`, `GuidHasher`, and the nine 64-bit `string` hashers — each of which already computed 64 bits internally and folded them away, so `Hash64` is the same mixer minus the narrowing. The 32-bit-only hashers (`Int32*` / `UInt32*`, the naive folds, `DefaultHasher<T>`) deliberately do not, since a key type narrower than 64 bits has no entropy to publish; a roster test pins that judgement. All five sketches route through it when the hasher provides it, via a compile-time type test the JIT folds away (so neither path allocates or branches) and with existing constructors and type parameters unchanged; on a 32-bit hasher `HyperLogLog` now applies the classical Flajolet large-range correction it previously skipped. `HashQualityEvaluator.Evaluate64` reports distribution over the 64-bit surface. Tracked in [#304](https://github.com/marius-bughiu/Celerity/issues/304).
- Implement `IReadOnlySet<T>` on the mutable sets and `IDictionary<TKey, TValue>` on the dictionaries. The sets implement `ISet<T>` and the dictionaries `IReadOnlyDictionary<,>`, but `ISet<T>` does not derive from `IReadOnlySet<T>` — so an ordinary BCL-shaped API taking either interface is a compile error against a Celerity type today. This is the same Guiding Principle #3 gap the 2.2.0 set-algebra work closed, one level up. Status: `done` — both halves. The ten mutable sets (`CeleritySet`, `SwissSet`, `RobinHoodSet`, `HashCachingSet`, `PooledCeleritySet`, `SmallSet`, `IntSet`, `LongSet`, `SparseSet`, `EnumSet`) now declare `IReadOnlySet<T>` alongside `ISet<T>`; every member the interface needs was already public and routed through the shared `SetOperations` helper, so the change is a declaration and nothing else. One consequence was worth taking on the chin rather than waving away with the BCL precedent: a call overloaded on *both* interfaces with no more-specific candidate becomes ambiguous, which is a genuine source-breaking change for downstream callers — `HashSet<T>` escapes it only because such libraries ship a concrete `HashSet<T>` overload to break the tie. It surfaced immediately as 14 ambiguous `Assert.Contains` sites in this repo's own suite, is recorded in the CHANGELOG under `Changed` with the cast that fixes it, and is documented next to the set-operations reference. `FrozenCeleritySet`, `CompressedIntSet` and `BTreeSet` already declared the interface and were untouched ([#306](https://github.com/marius-bughiu/Celerity/issues/306)). Nine dictionaries now declare `IDictionary<TKey, TValue?>` alongside the read-only interface — explicit-interface forwarders only, so no existing public signature moved and the concrete indexer still returns the non-nullable `TValue`. Two calls were worth recording. First, the `KeyCollection` / `ValueCollection` struct views were widened from `IEnumerable<T>` to `ICollection<T>` rather than boxing into a fresh adapter type, which is what keeps `dict.Keys` allocation-free on the direct path while `IDictionary<,>.Keys` still hands back a read-only `ICollection<TKey>` whose mutators throw, exactly as `Dictionary<,>.KeyCollection` does. Second, `EnumMap` was kept in rather than left out for its bounded key universe: an out-of-range enum cast is rejected with `ArgumentOutOfRangeException`, which *is* an `ArgumentException` — the failure `IDictionary<,>.Add` already documents for a key it cannot accept — so the implementation is honest rather than a member that throws where the contract says it should not; it is documented on both surfaces and pinned by a test. `Trie<TValue>` is the one mutable one-value-per-key dictionary deliberately left out: its `Keys` / `Values` are lazy `IEnumerable<T>` traversals, not counted views, so widening them is a design change rather than a forwarder. Tracked in [#307](https://github.com/marius-bughiu/Celerity/issues/307).
- Delete the per-probe virtual call. Guiding Principle #2 exists to remove exactly this. Status: `done` — the twelve open-addressed collections now route every vacant-slot test through an internal `EmptySlot.Is<T>` helper whose `typeof(T).IsValueType` guard the JIT folds, so a reference-type instantiation compiles to a plain null test and a value-type one keeps the existing intrinsic comparison unchanged. - Span-keyed lookups on the string-keyed collections. .NET 9's `GetAlternateLookup<ReadOnlySpan<char>>` lets the BCL `Dictionary` probe with a span key and no allocation; Celerity's string-keyed types require a materialized `string`, so the BCL is now *ahead* on the axis this library has invested most in. Status: `done` — `ISpanHashProvider` (`int Hash(ReadOnlySpan<char> key)`) ships as a standalone sibling interface in `Celerity.Hashing`, deliberately *not* deriving from `IHashProvider<T>`: that interface is generic in its key type, and a `ref struct` could not be a generic type argument before `allows ref struct` (C# 13 / .NET 9) while `net8.0` remains the floor — expressing the span overload as a non-generic sibling sidesteps that, because the span is a method parameter rather than a type argument. **The ordered / compressed integer-data lane.** Opened by the sorted-container hole — 38 collections and not one sorted map or set, with `Trie` the only ordered type, and that one string-keyed. The B-trees below close that half; the compressed-integer half is still open.

- `BTreeDictionary<TKey, TValue, TComparer>` / `BTreeSet<T, TComparer>` — cache-friendly sorted containers against `SortedDictionary<,>` / `SortedSet<T>`, which are red-black trees with a pointer chase and an allocation per node. Status: `done`. Tracked in [#305](https://github.com/marius-bughiu/Celerity/issues/305).
- `CompressedIntSet` — a Roaring-style compressed set of 32-bit integers, covering the huge-and-sparse shape that neither `BitSet` (dense, bounded) nor `SparseSet` (small universe, `O(Universe)` memory) nor `IntSet` (hash) serves. Status: `done` — the value space is partitioned into 65,536-value chunks, each stored as a sorted `ushort[]`, a 1024-word bitmap, or run-length pairs, whichever is smallest. The issue's kill criterion (≥3x faster intersect and ≥5x less memory at 1M elements over a 100M universe) was measured after implementation and cleared: **9.5x** on intersect at 1% overlap, **6.2x** at 50%, **11.5x** on union, **3.5x** on except, and **8.9x** less heap (17.7 MB → 2.0 MB). Two design calls are worth recording. First, the issue's "per-container-pair dispatch" was implemented as *two* paths per operator rather than nine — a word-parallel one for the dense bitmap⊕bitmap case and a cursor-driven one for everything else — because a run container that is only *read* must not be decompressed, and a single sorted-cursor abstraction gets that for free where nine hand-written pairs would each have had to re-derive it; the observable contract is still pinned for all nine pairs, in both operand orders, by `CompressedIntSetSetAlgebraTests`. The first draft of the cursor path probed with a binary search per element and measured only 2.7x on intersect — below the kill criterion — and was replaced with a linear merge of the two sorted cursors, which is where the 9.5x comes from; that is the single most load-bearing line of the implementation. Second, run containers are produced only by `Optimize()` and `AddRange`, never speculatively on a single insert, matching Roaring's own `runOptimize` contract. The type can hold all 2^32 `int` values, which does not fit the `int` that `ICollection<T>.Count` must return, so `Cardinality` (a `long`) is the always-correct count and `Count` throws `OverflowException` in the one case it cannot answer. Caveat #2 of the issue — no portable Roaring format, so no Lucene / Druid / Spark interop — was accepted rather than treated as a kill: the in-process memory and set-algebra win stands on its own, and it now leads both the API reference section and the README row. Tracked in [#310](https://github.com/marius-bughiu/Celerity/issues/310).
- `RankSelectBitVector` — succinct `Rank` / `Select` over a dense bit vector, the primitive the above compose on. Status: `done` — an immutable snapshot of a `BitSet` (or packed `ulong[]`, or a list of set positions) carrying a two-level popcount index: an `int` per 256-bit superblock and a `byte` per 64-bit word, so `Rank` is two index loads and one masked `POPCNT` and `Select` is a binary search over the superblocks. The issue's estimated 3% space overhead did not survive contact with the layout it specified — a byte-wide per-word counter caps the superblock at 256 bits, which puts the index at **25%** of the vector, the same price as the classic rank9 layout; `IndexSizeInBytes` reports it per instance and the docs lead with it. The build-once contract is stated first in every doc surface, and the benchmark ships the hand-rolled popcount loop as its baseline with the query position swept early / mid / late. Tracked in [#312](https://github.com/marius-bughiu/Celerity/issues/312).
- Sorted-span set algebra in `Celerity.Primitives` — merge-based `Intersect` / `Union` / `Except` / `IntersectCount` over already-sorted spans, where the BCL answer is LINQ or a `HashSet` round-trip. Status: `done` — `SortedSpan` ships the five entry points (`Overlaps` alongside the four above), generic over `IComparisonOperators<T, T, bool>` rather than as hand-written per-type overloads: the JIT specializes the merge per value type and each comparison lowers to one instruction, so the issue's fallback to explicit `int` / `long` / `uint` / `ulong` overloads was not needed. The kill criterion was measured and cleared with room to spare — at 1M × 1M over a 2M universe the scalar merge intersects in **6.1 ms against 25.7 ms** for `HashSet<int>` (**4.2×**; 5.7× vs LINQ) and allocates **0 bytes against 17.9 MB**, with union at 4.0× and except at 2.8× — and the asymmetric shape the galloping path exists for is where the real win is: **1k against 10M runs in 0.37 ms against 94.3 ms, 257×** (422× for `IntersectCount`). Three calls are worth recording. First, the **`Vector256` path was not shipped**, per the issue's own condition: the scalar merge is already memory-bound at 1M × 1M, and merge is branch-heavy enough that vectorizing it is frequently a wash — the kill criterion (≥25% over scalar) was never plausible enough to justify measuring a second implementation into existence. Second, **duplicates are collapsed rather than declared undefined**: every result is strictly ascending, which is what makes the `HashSet<T>` differential oracle meaningful and costs one predictable comparison per emitted element. Third, `Union` deliberately has **no galloping path** and `Except` gallops only when the subtrahend is the long side — in both excluded cases the result is proportional to the long input, so skipping comparisons cannot beat the cost of writing the answer out. The sortedness precondition is stated first in every doc surface and asserted in Debug builds only; a Release check would cost exactly what the algorithm saves. Tracked in [#313](https://github.com/marius-bughiu/Celerity/issues/313).

**A fourth core package: `Celerity.Sorting`.** `Array.Sort` / `MemoryExtensions.Sort` are scalar comparison introsort with no radix, counting, or selection path for primitive keys — and the BCL structurally cannot close it, because `Array.Sort` is contractually in-place while radix needs `O(n)` scratch. That is precisely the flexibility-for-speed trade this project's Vision licenses, against a named BCL counterpart. Layers on `Celerity.Primitives`, mirroring how `Hashing` and `Collections` layer today. Status: `done` — `RadixSort` ships the six primitive key types in keys-only, key+payload and `ArgSort` forms; `CountingSort` covers `byte` / `ushort` / declared-`[min, max]` `int` ranges; `PartialSort` is an introselect plus a bounded-heap `TopK`. Four design calls are worth recording. First, signed keys cost **nothing**: rather than transform the keys, the last digit's prefix sum starts at the sign-bit bucket, so only `float` / `double` pay the two extra linear passes an order-preserving bit transform needs. Second, the allocation-free overloads are named `SortWithScratch` rather than overloaded onto `Sort` — a `Sort(keys, scratch)` overload wins overload resolution over `Sort(keys, values)` whenever the payload has the same element type as the keys, so sorting `int` ids alongside `int` indices would have silently overwritten the payload; the differential test caught it on the first run. Third, the key+payload counting sort needs no key scratch at all: after the value scatter each counter has advanced to one past its run, which is exactly the run-end position the key rewrite wants. Fourth, `PartialSort` partitions three-way, so duplicate-heavy input stays linear, and carries an introselect depth budget that doubles as the guard stopping an inconsistent comparer from spinning forever. The issue's `float`/`double` caveat was accepted rather than papered over: `NaN` sorts by sign bit and `-0.0` before `+0.0`, both documented on the type, in the API reference and in the README, and both deliberately excluded from the `Array.Sort` fuzz oracle. Tracked in [#309](https://github.com/marius-bughiu/Celerity/issues/309).

- The benchmark suite is the most expensive thing in CI and nothing rationed it. Three issues turned out to be one lane. Runs *accumulated*: `benchmarks.yml` declared no concurrency group, so five pushes over one review loop created five uncancelled eight-shard runs and left `CI` and `Coverage` — the checks that actually gate correctness — queued for ~50 minutes behind numbers nobody would read ([#319](https://github.com/marius-bughiu/Celerity/issues/319)). Runs *overlapped*: with three branches in flight every shard measured 1.75–2.0x its baseline and one hit the 120-minute cap, on two pull requests whose diffs were **XML doc comments only** — and the worse failure is the quiet one, since a shard that completes under uneven contention still publishes its skewed delta ([#335](https://github.com/marius-bughiu/Celerity/issues/335)). And the two sides of the A/B were packed from *different class lists*, because greedy bin-packing is a function of the whole list and the PR head has a class `main` does not, so shard `i` was not the same slice on both sides and could pair a light head slice with a heavy base one ([#300](https://github.com/marius-bughiu/Celerity/issues/300)). Status: `done`. Three calls are worth recording. First, the concurrency key is the **PR number on the pull-request path and the commit SHA on the main path** — one group expression, but the main path lands every commit in its own group, so `cancel-in-progress` can never discard one and the published series keeps every point. Second, #335's own first choice — a global `concurrency: { group: benchmarks, cancel-in-progress: false }` — was deliberately **not** taken: GitHub queues at most one pending run per group and cancels the older pending one, so serializing would silently *drop* runs, which is a worse failure than slow feedback and defeats the point of measuring at all. What ships instead is the issue's option 2, which it rated the cheapest and most obviously correct: a relevance gate that does not run the suite when the diff cannot move a number. It is one-directional by construction — only documentation, the three projects `Celerity.Benchmarks.csproj` does not reference, and `.cs` files whose text is unchanged once comments are stripped can be skipped; an added file, a `.csproj`, or a git command that fails all run — and it is applied to pull requests only, so `main` always measures and a gate mistake costs a missing PR comment rather than an unseen regression. It correctly skips both pull requests #335 names and runs on every code change tested against it. The comment-stripping rests on a real C# scanner rather than a `//`-prefix test, because `//` occurs inside literals and C#'s verbatim / interpolated / raw forms desynchronise a guess; a `--self-test` pins it in `ci.yml`. Third, #300 was closed by having the base **replay** the head's resolved class list instead of packing its own, which makes the base a subset of the head by construction — the pair is then bounded by twice the head slice, the quantity the packer already balances. The job timeout was raised as well, but only after that bound existed and only against measured numbers: the eight head slices ran 45.8–67.3 min, so the bound is 91–135 min and the two heaviest shards exceeded the old 120-minute cap on their own. That cap was set when the suite was smaller and `Celerity.Sorting`, `SortedSpan` and `SegmentTree` have since added classes, so raising it is sizing the budget to the measurement rather than the option-3 move of buying room for an imbalance. Widening the matrix was rejected instead: the 81-case `StringHasherBenchmark` is a single class and sharding is by class, so it floors the heaviest slice however many shards there are, and more shards means more concurrent runners — the contention #335 is about. One trap is worth recording, because the first attempt hit it and only a full CI run could show it: the base step executes the **`main` worktree's** code, so a selector flag it does not yet have matches nothing and it runs the entire suite rather than one slice. Both selectors are therefore passed until the new one is on `main`. Option 4 of that issue shipped alongside: a report missing a shard now says so above the fold, since the failure mode was that a partial comparison read exactly like a complete one. **Since superseded by the blunter fix this lane kept circling:** the suite no longer runs on pull requests at all, only on merges to `main` and on manual dispatch. Rationing a per-PR eight-shard A/B three separate ways still left it the largest line in the Actions bill, re-paid on every review commit — so the base half, the per-PR concurrency key and the shard-list replay it needed all went with it, and the relevance gate now applies to `main` too.

- The fourth issue in that lane is its reporting half: the comment flagged noise as regressions. A row was flagged when it moved past ±10% *and* past the two measurements' summed standard deviation — but that compares a **between-run** difference against **within-run** dispersion, and BenchmarkDotNet's `StandardDeviation` describes the spread of iterations inside one settled process, not the JIT / GC / page-cache drift that actually separates the head slice from the base one. The guard was therefore systematically too permissive: on a pull request whose library IL was byte-identical to `main` it flagged 13 rows, among them four on BCL baseline arms — `Dictionary` and `HashSet` methods, the same code on both sides by definition. At that rate the default reading of a flag is "probably noise", which is the same as having no signal — and it buries a real regression in a list of a dozen false ones, in a project whose fourth guiding principle makes the published numbers the contract. Status: `done` — the rule moved out of `benchmarks.yml` into `scripts/benchmark_comment.js`, where it is runnable and pinned by a `--self-test` in `ci.yml`; the noise bar became **3σ** over the two standard deviations added in quadrature rather than a 1σ sum; and the comment now publishes the run's own observed spread (p50 / p90 / p95 of |Δ| across every paired row), so a flag can be read against the run it arrived in instead of against an assumed floor. Replayed over that zero-IL run it cuts 13 flags to 2 while still detecting every regression on a benchmark precise enough to resolve one. A row whose `main` side failed to measure now counts toward the warning total, where it previously sat in the table under a summary line reading "No significant change vs main". **The comment has since been removed**, with the suite moved to post-merge-only: the per-PR A/B was the single largest consumer of this repository's Actions minutes, re-paid on every review commit, and a regression is now read off the dashboard at the merge commit instead. `scripts/benchmark_comment.js` went with it. Tracked in [#351](https://github.com/marius-bughiu/Celerity/issues/351).

**Identified after the review, by the same source-reading convention.** The Q3 survey rostered twelve items; the following were found afterwards, by reading the shipped surface rather than by the plan, and are filed against this lane as they are identified.

- `SegmentTree<T, TMonoid>` — range aggregates over an arbitrary associative fold. The gap was written down in the library's own documentation: the `FenwickTree<T>` section of the API reference closed by saying a segment tree "are the next step (not shipped)". Fenwick is constrained to `INumber<T>` for a structural reason, not a stylistic one — its range query is the *difference* of two prefix folds, so the operation must have an inverse — which left the entire non-invertible half of the range-query space (min, max, gcd, bitwise and/or, any user-written fold) unreachable, with no BCL counterpart either. Status: `done` — `IMonoid<T>` ships as a `struct` type parameter alongside five built-in folds, so `Combine` inlines rather than costing a virtual call per level. Three calls are worth recording. First, the layout is the flat **`2n`** array, not the power-of-two-padded `4n` one that is usually recommended: the objection to `2n` is that the leaves sit in a rotated order at non-power-of-two lengths, so an internal node can span a wrapped range — but a query that walks outward from both ends into two separate accumulators never combines such a node into the wrong side, and an exhaustive differential sweep over every length and every range under a **non-commutative** fold pins that. A commutative fold cannot observe the difference, which is why min/max/sum could not be the oracle and the fuzz target and the differential suite both run "first non-zero wins" and string concatenation instead. The one visible consequence is that `Aggregate` is a query rather than a root read. Second, **lazy propagation was left out** rather than half-shipped: range updates need a second monoid describing how updates compose plus a distributive law relating the two, which is a different type with a different contract, and it is stated as an exclusion on every doc surface. Third, `T` is deliberately **unconstrained** — a `string`-concatenation monoid is a legitimate fold and the tree's own storage does not care — where the sibling `FenwickTree<T>` is `struct, INumber<T>`. The kill criterion (≥10x over the array scan on interleaved update + range-min at 100k) was measured after implementation and cleared at **14.8x**, with **81x** on a query batch against a pre-built tree; at 1k it is only 1.4x, and the README and API reference both lead with that rather than quoting the headline alone. The floating-point caveat on `MinMonoid` / `MaxMonoid` (the identity is the largest / smallest *finite* value, and a `NaN` resolves by operand position) is documented on the type, in the API reference and in the tests. Tracked in [#348](https://github.com/marius-bughiu/Celerity/issues/348).

- `KdTree<TValue>` — the spatial axis, which the roadmap named and never delivered. Milestone 2.0.0's "specialized collections for domain-specific workloads (e.g. graph traversal, **spatial indexing**)" was closed on four streaming sketches that have nothing to do with the spatial question, so 56 collection types shipped without one that indexes the plane — and .NET has no k-d tree, quadtree, R-tree or spatial index of any kind either, leaving an array measured in full on every query. Status: `done` — a build-once immutable 2-D k-d tree: one interleaved coordinate array with a balanced tree laid over it implicitly (median by introselect per level, alternating axes), no per-point node, nearest / k-nearest / radius / rectangle queries sharing two traversals that are generic over `struct` regions and visitors, and a k-nearest search whose bounded max-heap lives in the caller's own buffer so it allocates nothing. Three things are worth recording. First, **the kill criterion was missed and the type shipped anyway, deliberately**: the issue asked for >=10x on nearest-neighbour and >=5x on the radius query at 100,000 points *against both* baselines, and while the naive scan is beaten by 348x and 53x, the better hand-roll — points ordered by x, scanned outward from the query, abandoned on the horizontal gap, which is effectively a one-dimensional spatial index — is beaten by only 2.5x and 3.5x, and at 1,000 points that margin falls to 1.4x on the nearest query and vanishes on the radius one (all quoted from CI's same-runner A/B, which differed from a development machine by enough to move this claim). The bar was set against a baseline that turned out to be far stronger than expected; the judgement is that a total BCL gap plus two orders of magnitude over the idiomatic alternative is what the hard rule asks for, and that requiring a library type to beat a bespoke competing index tenfold was the wrong bar rather than the wrong result. Every surface quotes both columns and the 1,000-point crossover rather than the headline alone. The build uses introselect rather than plain quickselect because review surfaced that the degenerate input for a middle-element pivot is an ordinary one — an **organ pipe**, ascending interleaved with descending, the shape of any path that goes out and comes back, which at 4,096 points costs 2,048 passes against a budget of 24 and takes a single selection quadratic; the depth budget mirrors `PartialSort.SelectCore` and bounds the build at `O(n log^2 n)`. Second, an **interleaved coordinate layout was measured, not assumed**: predicted to help because every node a query reaches needs both coordinates, it came out inside the run-to-run spread (168.4 us against 165.9 us) and is kept for the smaller invariant, with the comment saying so. Third, a **shape control refuted its own hypothesis, twice over** — clustering was expected to punish the one-dimensional baseline and instead *reverses* the comparison, the hand-roll winning at 0.94x against 1.92x on uniform points, because a query drawn from inside a cluster has a very near neighbour and that is exactly what lets the scan abandon early. Review then caught that the first version of the control derived each query from a stored point plus another deviate, compounding two Gaussians into `centre + N(0, 2s^2)` so queries sat in the sparse fringe of each blob and the clustered figure came out at a flattering 1.12x; queries are now drawn afresh from the same generator as the points. `KdTreeShapeBenchmark` keeps the measurement, the reasoning and the bias that had to be removed to get it. 2-D specifically rather than generic-`k` (a `ReadOnlySpan<double>` boundary and an array per point would cost the flat layout the type exists for), and `double` coordinates rather than `INumber<T>` (squared distances overflow an integer type silently). Tracked in [#366](https://github.com/marius-bughiu/Celerity/issues/366).

- `SpatialGrid<TValue>` — the spatial axis for points that **move**, which `KdTree` (#366) documented itself out of: *do not reach for it when the points change constantly — it is build-once, and rebuilding per frame costs more than the queries save*. That is the commonest spatial workload rather than an edge case, and .NET has nothing for it either. Status: `done` — a mutable, bounded uniform-cell grid: one array of cell list heads and one array of fixed-size entry records threaded through them by an intrusive doubly-linked list, with payloads in a third array the cell walk never touches, so a populated grid carries no per-cell and no per-entry object. `Add` returns a `SpatialGridHandle`, and `Move` / `Remove` / `TryGetPoint` take one, which is what makes relocation `O(1)` — a coordinate write plus, only on a cell crossing, an unlink and a relink — with no hash of the coordinates and no equality contract on the payload. Slots carry a version stepped on vacate, so a handle retired by `Remove` or `Clear` is rejected rather than silently addressing whatever reused the storage. Four calls are worth recording. First, **bounded rather than hashed cells**, which the issue left open: a declared world buys a dense cell array and index arithmetic instead of a tuple hash, and an out-of-world point is *clamped* into the edge cell rather than rejected — correct because the clamp is monotone and a query's own cell range clamps identically, which the differential suite proves by generating a slice of its points outside the world. Second, **no `TrimExcess`**: a handle *is* a position in the entry array, so compacting it would invalidate every handle a caller holds, which is the one thing the type promises not to do. Third, **no k-nearest**: bounding a ring search by the k-th best rather than the best weakens the ring bound badly, and the workload this type exists for is a radius query. Fourth, `Move` deliberately **does not invalidate enumerators** — it changes neither the set of entries nor the slot each occupies — which is the family's no-op rule applied to the operation the type exists for, pinned in the shared suite next to `FenwickTree`'s zero delta.

  The pre-registered kill criteria were measured after implementation and the result is mixed, recorded here rather than rounded away. The first bar — **≥5x** over the `Dictionary<(int, int), List<T>>` hand-roll on a frame of 100,000 entities (move a tenth, then one radius query each) — is **met at 5.02x**, and that is the bar the issue said the type lives or dies by. It is worth recording *how narrowly*: 9.83 ms against 1.96 ms on CI's same-runner A/B clears the bar by 0.4%, against a combined run spread of about 1.5%, so it passes by less than the noise. A development machine said 5.5x, and quoting that instead would have turned a marginal pass into a comfortable-looking one — the requote is the whole reason this repo insists on CI figures. The second bar — **≥50x** over rebuilding a `KdTree` per frame, which the issue called the easy one — is **missed at 13.3x**, because a frame is not only the rebuild: both arms also run 10,000 radius queries, and that shared work sits in the denominator however cheap the index makes it. More important than either is what the shape control found: **the margin is a property of how full the cells are, not of the type**. Both structures walk the same cells and test the same candidates, so everything gained is *per cell*, and the ratio collapses as cells fill — 6.5x at ~1 point per cell, **1.12x** at ~10, and **0.52x on clustered data, where the hand-roll wins outright**. That last row refuted the hypothesis it was written to confirm (that clustering would hurt both equally, the baseline being the same grid): inside a dense cell the layouts do differ, because the hand-roll walks a contiguous `List<T>` with independent per-candidate loads while the grid walks an intrusive list whose every step is a load that must complete before the next address is known. So the type's documented failure mode is sharper than "it degrades to a scan" — it degrades to a scan the hand-roll does faster. **A second claim did not survive review either**, and it is the more instructive one: every surface originally sent clustered points to `KdTree`, reasoning that pruning adapts to density where a fixed cell size cannot. That inference chained two unrelated comparisons — this control against a `Dictionary`, `KdTreeShapeBenchmark` against an x-sorted scan — and nobody had measured the one a caller actually faces. A third arm now does, and the consolation is not there: on clustered moving points a per-frame rebuild is **level** with the grid (24.3 ms against 24.0 ms) while the hand-roll takes 12.5 ms. For heavily clustered points that move, neither Celerity type helps, and every surface now says so. Every surface also leads with the density dependence rather than with the headline. Tracked in [#371](https://github.com/marius-bughiu/Celerity/issues/371).

- `RTree<TValue>` — the spatial axis for objects that **occupy an area** rather than sitting at a coordinate, which `KdTree` (#366) structurally cannot index: a box can overlap the query while its centre sits far outside it, the two-dimensional form of exactly the argument that made `IntervalTree` (#361) necessary next to `BTreeSet` on one axis. .NET has no R-tree, no bounding-volume hierarchy and no extent index of any kind either. Status: `done` — a build-once immutable index bulk-loaded by **STR (Sort-Tile-Recursive) packing**, with a fixed-fanout (16) tree laid over the packed entries *implicitly*, so leaf `i` owns entries `[i*16, i*16+16)` and every node above owns the same fixed run of the level below: no per-node object, no child pointers, one flat array each for extents, payloads and node bounding boxes. The packing is applied recursively from the root down rather than once per level, which is what keeps the layout implicit. Both kill criteria the issue set *before* implementation were cleared, which is the point of having set them there: 141x over the naive scan against a bar of 10x, and **9.6x** over the sorted hand-roll against a bar of 3x — the bar written modestly because `KdTree`'s analogous one-dimensional baseline came in at a surprising 2.5x and that argument should not be had after the fact. Three things are worth recording. First, **the received wisdom about shape did not survive being measured, and the type is documented as refuting it rather than as confirming it**: the issue, the standard literature and this repository's own first draft all said an R-tree earns its keep only on extents spanning orders of magnitude and that uniformly sized boxes belong to a bucketed grid. Giving the grid an arm of its own — required by this repo's rule that a *use X instead for shape Y* claim needs its own benchmark rather than an inference chained from two others — showed the tree 1.30x ahead of the grid on the varying shape and **3.01x ahead on the uniform one**, its widest margin on the shape it was expected to lose, because a grid's query cost is dominated by the cells a query covers while an R-tree's node boxes get *tighter* as extents get more alike. The qualification kept alongside it is that a grid's cell size is a tuning knob sized here by the data rather than by the query; the surviving reason to reach for a grid is mutability, not shape. Second, the **packing choice was measured rather than assumed**, which #369 had just made possible: on a common harness where only the permutation differs, sort-tile is 1.04x ahead of a Hilbert order on varying extents and 1.21x ahead on uniform ones, so the shipped choice is the measured one. Review caught the first version of the shape control confounding itself — the uniform arm used the range's *geometric* mean, giving those boxes 21x less area and shrinking the grid's cells, so it varied size and selectivity along with spread; at the arithmetic mean the conclusion survived and strengthened. Third, **one query region rather than two** — a point query is an overlap query against a degenerate box, so the traversal is generic over the visitor alone and the closed-edge rule is what makes that identity hold. Cross-collection shared suites do not apply, confirmed by grep rather than assumed: every one of them is keyed on the dictionary/set families, and `KdTree`, `IntervalTree`, `XorFilter` and `RankSelectBitVector` appear in none of them either. Tracked in [#370](https://github.com/marius-bughiu/Celerity/issues/370).

- The bare `UIntNN Hasher` name meant opposite tiers of the escalation ladder in the two unsigned widths: `UInt32Hasher` was the cheap XOR-fold while `UInt64Hasher` was the strong Murmur3 `fmix64` finalizer, so a caller who benchmarked on `uint` and then moved to `ulong` keys by analogy silently changed hash *strength*, not just key width. Hasher selection is the main knob this library exposes and the signed families never had the problem, because they name the algorithm in the type. Status: `done` — option 1 of the issue (rename for explicitness, old names kept as `[Obsolete]` aliases until a future major version): `UInt32WangNaiveHasher` and `UInt64Murmur3Hasher` ship, and the aliases forward to them rather than repeating the mixer, so the pairs cannot drift and no hash value moved. Two calls are worth recording. First, `UInt64Hasher` keeps its `IHashProvider64<ulong>` implementation rather than being reduced to the 32-bit surface: dropping it would push an existing sketch back to the 2^32 entropy floor `IHashProvider64<T>` exists to escape, silently, as a side effect of a *naming* change. Second, the identity tier was left signed-only, and that was recorded as an open gap rather than a decision: the first draft argued an unsigned key reaches the zero-work floor with a cast at the call site, which is false for the primary use case — the collections constrain `THasher` to `IHashProvider<TKey>` and invoke `Hash` internally, so no `IHashProvider<uint>` identity hasher means no zero-work floor for a `uint`-keyed collection at all. Filed as [#357](https://github.com/marius-bughiu/Celerity/issues/357) rather than settled inside a naming change, and closed there: see the entry below. The regression guard is the family-wide `IntegerHasherFamilyNamingTests`, which fails on a new bare-named integer hasher or a width missing a tier; it also pins the one unsigned/signed pair that is deliberately *not* bit-identical, the 32-bit naive fold, whose shift is arithmetic on `int` and logical on `uint`. Tracked in [#297](https://github.com/marius-bughiu/Celerity/issues/297).

- The zero-work identity tier existed only for the signed integer widths, so a `uint`- or `ulong`-keyed collection or sketch could not be given a no-mixing hasher at all — the cheapest reachable option was the XOR-fold, and the documented "uniform / trusted keys → skip mixing" rule had nothing to point at for half the integer widths. Status: `done` — `UInt32IdentityHasher` and `UInt64IdentityHasher` mirror the signed pair exactly, including the 64-bit one's low-32-bits truncation and its deliberate abstention from `IHashProvider64<T>` (a truncating pass-through has no 64-bit code to publish, so a sketch parameterized on it correctly keeps the 32-bit path — which for `HyperLogLog` means the classical large-range correction stays engaged instead of being skipped on a false claim of 64-bit entropy — now pinned by the `HashProvider64ContractTests` negative roster rather than left to convention). `Identity` joined the tier list in `IntegerHasherFamilyNamingTests`, so a future width cannot ship without one, and the cross-width bit-pattern agreement tests cover it alongside the mixers. The `uint` hasher is worth distinguishing from its `ulong` sibling: `uint` and `int` are the same width, so the cast is a reinterpretation and identity stays a bijection — nothing is lost, unlike the 64-bit truncation. Tracked in [#357](https://github.com/marius-bughiu/Celerity/issues/357).

- Nothing guarded the package-validation baseline itself. The binary-compatibility gate added by [#315](https://github.com/marius-bughiu/Celerity/issues/315) is only as strong as the version it compares against, and that version is bumped by a *manual* follow-up commit after each release — deliberately, since it becomes a `PackageDownload` and cannot point at anything unindexed. The bump was skipped for v2.6.0 and nothing noticed for the whole cycle: every package validated against its 2.5.0 predecessor, so a break introduced *in* 2.6.0 would have packed green, and `Celerity.Sorting` still carried the first-release escape hatch, which does not narrow the gate but removes the package from it. Both states pack green, which is the whole problem — the fourth instance of the shape already guarded in [#314](https://github.com/marius-bughiu/Celerity/issues/314), [#339](https://github.com/marius-bughiu/Celerity/issues/339) and [#301](https://github.com/marius-bughiu/Celerity/issues/301), and the last one still unchecked. Status: `done` — `scripts/check_package_baseline.js` runs as the `package-baseline` job on every PR and asserts that the baseline equals the highest stable version published by every *gated* package. Three calls are worth recording. The invariant is stated against **NuGet.org's published versions rather than the newest git tag**, which is what removes the need for a grace period: the baseline is legitimately one release behind between the tag and indexing, so a tag-based rule could only tolerate that by permitting a one-release lag in general — precisely the drift that went unnoticed, meaning such a rule could never have caught the thing it was written for. Asking what is actually published makes the bump due the moment the release is indexed, and catches a bump that lands too *early* as well. Second, the comparison is against the version published by **all** gated packages rather than the newest on NuGet, because one shared property resolves a `PackageDownload` for all seven and `Celerity.Sorting` has no 2.5.0 to download; packages still on the escape hatch are excluded from that intersection rather than counted as unpublished, so an eighth package can be added without invalidating everyone else's baseline. Third, the check reaches the network, where the three sibling guards are hermetic — so an unreachable NuGet.org is reported and skipped rather than failed, on the reasoning that a guard which reds a pull request over an outage gets ignored, and this one runs on every PR. The seven package ids are discovered from the `.csproj` files rather than listed, so the guard cannot itself go stale when a package is added. **Since removed along with the gate it guarded** — a guard on a guard was the cost that decided [#315](https://github.com/marius-bughiu/Celerity/issues/315)'s removal, and it had nothing left to check. Tracked in [#364](https://github.com/marius-bughiu/Celerity/issues/364).

- `IntervalTree<TKey, TValue, TComparer>` — the interval axis, which nothing shipped could reach. The library had covered the *position* axis three times over (`FenwickTree`, `SegmentTree`, `RankSelectBitVector`) and the ordered axis twice (`BTreeDictionary` / `BTreeSet`, `Trie`), but "which ranges cover this point" had no answer in it — and none in the BCL either, which ships no interval tree, no interval map and no range-overlap query on any of net8/9/10. Status: `done` — a build-once, immutable augmented interval tree: the intervals sort by start into flat parallel arrays with a balanced BST laid over that array *implicitly* (the node for `[lo, hi)` sits at its midpoint and owns exactly that range), so there are no nodes and no per-interval heap object, and each node carries the maximum end over its subtree, which is the bound that turns the scan into a search. Three calls are worth recording. First, every query shape — the early-exit predicates, the counts, the buffer copies — shares **one** traversal generic over a private `struct` visitor, so the JIT specializes it per call site and inlines the per-match work; four hand-written walks or a delegate per match were the alternatives, and this is the same rule `IMonoid<T>` and `DefaultComparer<T>` already follow. Second, the `ReadOnlySpan<Interval<,>>` constructor that the first draft shipped alongside the `IEnumerable<>` one was **removed**: it makes the commonest argument of all — an array — ambiguous under C# 12, which is what `net8.0` compiles as, while resolving cleanly on a newer language version, so the break would have landed only on the oldest supported consumers and only there. The test suite caught it because CI builds every TFM. Third, an **empty** interval is stored and enumerable but never reported by a query, rather than rejected at construction: a half-open `[x, x)` covers no point, so it shares none, and silently dropping a caller's input is worse than carrying it. The kill criterion (≥10x over the `List<T>` scan on point stabbing at 100k) was measured after implementation and cleared at **129x** — and, against the *better* hand-roll that a review round asked for and that is now benchmarked as its own arm (a start-sorted list, which cannot skip the front of the list but can stop once the starts pass the query), **19x**, which is the number the type should be judged by — with **75x** on the window query and **19x** on the first-overlap conflict check (all from CI's same-runner A/B, which is what the dashboard publishes; the local figures the docs first carried were 151x / 13.9x / 79x / 27x, and the conflict-check one flattered the type) — but the number that matters more is the one that qualifies it: the tree's work tracks the matches found, so on a shape ten times denser (~1,250 matches per point) the same query falls to **8.3x** in a local control, and both the README and the API reference lead with that dependence rather than the headline alone. The advertised bound was corrected under review from `O(log n + k)` to `O(log n + k)` clustered / `O(min(n, (k + 1) log n))` scattered, with `O(n)` unconditional once empty intervals are stored: the max-end augmentation proves only that a subtree *contains* a candidate, so scattered matches can force separate root-to-match descents, and the stronger bound belongs to a centered interval tree with per-node sorted endpoint lists rather than to this layout. Start-ordered storage is what makes the clustered case the common one. Build costs 28x a `List<T>` fill and 2.3x its memory, paid once — the memory figure came down from 3.3x under review, when the constructor started sizing a counted source exactly instead of routing it through a `List<T>`. Tracked in [#361](https://github.com/marius-bughiu/Celerity/issues/361).

- `MortonCurve` / `HilbertCurve` — the space-filling-curve primitive, which is what lets a *one-dimensional* structure answer a spatially local question. `Celerity.Primitives` already shipped the bit-level toolkit (`SpanBits`, `Branchless`, `VarInt`, `BitReader` / `BitWriter`) and none of it could map a 2-D coordinate to one integer that preserves locality; neither can the BCL, whose `BitOperations` has no bit-interleave and which ships no Hilbert anything. That mattered here specifically, because the library is now full of excellent one-dimensional structures a curve makes spatial. Status: `done` — `MortonCurve` is the five-step magic-number spread (2-D lossless over both `uint` axes and bijective onto `ulong`; 3-D capped at 21 bits per axis), `HilbertCurve` is Skilling's transpose transform composed with Morton's own interleave, since the transposed axes interleave to give the Hilbert index and reusing `Encode2D` / `Encode3D` for that step is what keeps the second curve short enough to audit. Three calls are worth recording. First, **the `Bmi2` path was measured and deliberately not shipped, which is a departure from the issue rather than a confirmation of it**: the issue's first kill criterion said the intrinsic ships only if it beats the portable fallback measurably, and it does — `PDEP` / `PEXT` come in at 3.8x the portable spread on the development machine's Intel part. It is still not shipped, for two reasons the criterion did not anticipate. `Bmi2.IsSupported` is `true` on AMD Zen 1 and Zen 2, where both instructions are microcoded and an order of magnitude *slower* than the portable sequence, and .NET exposes nothing that distinguishes those parts — so a blind dispatch trades a win on one vendor for a large regression on another. And this repository gates on 100% line *and* branch coverage, under which exactly one arm of a hardware dispatch is reachable on any given runner: the other ships unexecuted by the suite, and `[ExcludeFromCodeCoverage]` would be excluding the arithmetic itself rather than a guard. The intrinsic is carried in `SpaceFillingCurveBenchmark` instead, so the decision stays measurable and can be revisited. **This is the one judgement in the item a maintainer might reasonably reverse.** Second, the first draft of `HilbertCurve` measured **173x** `MortonCurve` and now measures **43x**, a 4.0x improvement found by benchmarking it rather than by reading it, and the two steps did not cost what they looked like they would. Writing the transform out per arity instead of looping over a `Span<uint>` of axes — the obvious suspect, since a conversion makes ~200 span accesses each carrying a bounds check — was worth only **1.4x**. The other **2.9x** came from routing every per-level decision through `Branchless.Select`: the deciding bit is one bit of a coordinate, so each of the ~90 branches a conversion takes is a coin flip the predictor cannot learn, and the mispredictions rather than the arithmetic were most of the cost. The library's own primitive turned out to be the fix for its newest one. Third, `Encode3D` **throws** on a coordinate above 2^21 - 1 rather than keeping the low bits, because masking would round-trip a *different* point back to the caller, which is worse than refusing input the caller got wrong. The second kill criterion — that the curve must be shown *earning* its place on a cache-bound sweep, not merely existing — was measured after implementation in `SpaceFillingCurveLocalityBenchmark`, which lays the same point set out four ways and runs one identical neighbourhood sweep over each: at 2 million points (32 MB per layout — far past any private L2, and past the 30 MB last-level cache of the machine this was measured on, though last-level cache sizes vary) an identical batch of randomly-located neighbourhood queries runs **1.77x** on the Morton layout and **1.84x** on the Hilbert one against the same points unsorted, which clears the bar as the issue wrote it — but against the *smarter* baseline the repo's own convention demands, a row-major cell key, the margins are **1.15x** and **1.19x**, and that is the pair every surface leads with. At 100,000 points the whole set fits in cache and all four layouts measure the same to within 4%; that control is a benchmark parameter rather than a footnote. The first version of the payoff benchmark measured **no difference at all** and was wrong rather than informative: it swept one aligned block of cells, which touched a small enough slice of the point set to stay resident in L2 whatever order it was stored in, so there were no misses left for a layout to save. Randomly-located queries are what removed the reuse. Tracked in [#369](https://github.com/marius-bughiu/Celerity/issues/369).

- `CompressedGraph` — the **graph** axis, and the other half of the sentence `KdTree` (#366) paid off. Milestone 2.0.0 rostered "specialized collections for domain-specific workloads (e.g. **graph traversal**, spatial indexing)" and closed it on four streaming sketches; the spatial half was later recognized as unclosed and paid off three times over, and the graph half never was. 63 collection files later nothing represented a graph — `SparseSet` is the *visited set* a traversal needs and `DisjointSet` is a connectivity oracle that cannot enumerate a vertex's neighbours, so both sit next to the gap rather than in it. .NET has no graph, adjacency structure or traversal of any kind either. Status: `done` — a build-once immutable directed graph over dense vertex ids in compressed sparse row form: an offset per vertex and one contiguous target array, so `Neighbors(v)` is a `ReadOnlySpan<int>` slice rather than a `List<int>` object per vertex, with the targets sorted at build time so `ContainsEdge` binary-searches and duplicate edges collapse. `Reverse()` is the transpose as an `O(V + E)` counting scatter; the breadth-first and Kahn topological orders both use the caller's destination buffer as their queue, so the only other state is a bitmap or in-degree array rented from `ArrayPool<T>`.

  **One of the two pre-registered kill criteria was missed, and the type shipped anyway — recorded here rather than rounded away.** The issue set ≥3x on a full breadth-first traversal against `Dictionary<int, List<int>>` and ≥2x less managed heap, and said that missing either meant closing it unshipped. At 100,000 vertices and average degree 8 the heap bar clears at **3.60x** (3.60 MB against 12.97 MB retained, measured with a settled GC rather than read off the allocation column, which counts transient build buffers and says 1.88x). The traversal bar **misses** on CI's own same-runner A/B, at 2.5–2.6x across two runs — and the two explanations written for that miss were themselves wrong, in the same way, twice. That is the part worth keeping, because correcting it is what settled the type's actual case.

  The first explanation blamed a baseline whose neighbour arrays land consecutively. Review pointed out the benchmark never built such a thing (`List<int>` grows its backing array in the order the edges arrive, so the data scatters however tidily the list objects were created), and a tight `int[][]` arm added to test the claim refuted it. The second explanation then leaned the whole case on the transpose, the build and the footprint — while those were still measured only against `List<int>[]` and `Dictionary<,>`. Review caught that too. Tight `int[][]` baselines now exist for the transpose and the build, and a retained-size measurement for the jagged form, so **every published ratio names the baseline it was measured against.**

  Against `int[][]` sized exactly and filled in vertex order — the best hand-roll, and held to the same standard as the type it bounds: it reuses its count array as the scatter cursor exactly as this type reuses its offsets, and shares `Array.Empty<int>()` for empty rows since this type has no per-row object at all. Both of those came out of review, and both moved the numbers against this type. **Across two CI same-runner A/B runs** at 100,000 vertices and average degree 8: traversal **1.15–1.28x** (and a **loss** at 1,000 vertices), build **1.16–1.29x** (also a **loss** at 1,000, while allocating about 1.5x more during the build), transpose **2.5–3.0x**, retained heap **1.83x** less. Two corrections about *measurement* are worth recording with the rest, because they cost more review rounds than the code did. First, the local development numbers this entry originally carried differed from CI's by up to 35% in both directions, so every figure was replaced once the A/B ran. Second — and this is why the numbers above are ranges — two CI runs of *identical code* then disagreed by up to 20% on the allocation-heavy arms (transpose 2.46x and 3.01x; build against `Dictionary` 3.05x and 3.80x) while the pure-compute arms held to about 1% (neighbour iteration 1.37x and 1.36x, topological 1.97x and 1.95x). Quoting any single run to three digits would claim a precision this benchmark does not have. Against the idiomatic `Dictionary<int, List<int>>` the same arms are 2.5–2.6x, 3.1–3.8x and 3.60x. So what actually survives contact with a competent hand-roll is the transpose — structurally, since the jagged form must allocate a row per vertex where CSR scatters into arrays it already has — the footprint, and not having to write, test and maintain the traversal, Kahn's algorithm, the transpose, the deduplication and the sorted-target invariant on a structure the BCL does not ship at all. **The type is not a speed win over a well-laid-out `int[][]` and no surface claims it is.**

  The traversal arms are also end-to-end rather than layout-isolating (the baselines mark visits in a `bool[]`, the type in a `ulong` bitmap — 12.5 KB against 100 KB), and the topological arm has no tight counterpart, so its 1.97x is against `List<int>[]` and should be expected to shrink the same way. The call to ship therefore rests entirely on the BCL-gap limb of the hard rule. **It revises the issue's own stated consequence for a miss, so it is flagged as awaiting maintainer confirmation rather than treated as settled — and the narrowed case makes that call harder, not easier.** The honest caveat travels with the number on every surface: the win is a memory-hierarchy win, and at 1,000 vertices — the whole graph in cache — the traversal is a **loss** against the tight hand-roll. Weighted edges and shortest paths were left out as algorithms over a container rather than the container. Tracked in [#381](https://github.com/marius-bughiu/Celerity/issues/381).

- `SuffixArray` — the **text** axis, which nothing shipped could reach. The library indexed positions three times over (`FenwickTree`, `SegmentTree`, `RankSelectBitVector`), intervals, space three ways and graphs, and text not at all: `Trie<TValue>` indexes a *set of keys* by their prefixes and structurally cannot say where a substring occurs inside one block of text. .NET cannot either — `string.IndexOf`, `MemoryExtensions.IndexOf` and `Regex` are vectorized scans that re-read the text on every query, and .NET 9's `SearchValues<string>` indexes the patterns rather than the haystack, so the fixed-text, many-queries shape that log, document and source-code search all have has nothing in the box. Status: `done` — every suffix start position in lexicographic order, built by prefix doubling over the cyclic shifts with a sentinel appended (a counting sort per round, `O(n log n)`, every scratch buffer rented from `ArrayPool<T>`), with Kasai's longest-common-prefix array beside it in `O(n)`. The matching suffixes are contiguous in the order, so `CountOccurrences` is the width of a range and `TryGetOccurrences` is a slice of the index's own array with no copy, and the longest repeated substring falls out of the LCP array in one linear pass. Two baselines are measured, not one: the `IndexOf` scan the BCL ships, and the `Dictionary<string, int[]>` k-gram inverted index a competent caller writes instead — which **wins by 10.3x** on query cost at the one pattern length it can answer and is published saying so. Both pre-registered bars clear on CI's own numbers at 100,000 characters: **68x** the scan on counting a present pattern and **64x** on ruling out an absent one, against a ≥20x bar on each. The build is repaid at roughly **1,000** counting queries, falling to about 1.3x margins and a ~3,900-query crossover at 1,000 characters — published rather than rounded away, because below the crossover `IndexOf` is the right answer. Tracked in [#386](https://github.com/marius-bughiu/Celerity/issues/386).

- `AhoCorasick` — the **multi-pattern** axis, the other half of the text one and reachable from neither side of it. `SuffixArray` (above) closed the fixed-text, one-pattern-at-a-time shape; the mirror shape — a fixed *pattern set* and a text that keeps arriving — had no answer here or in .NET. `Trie<TValue>` matches a prefix of the *query* and structurally cannot resume at position 1, 2, 3 … of a text, `SuffixArray` would need an index per text, `string.IndexOf` is one needle per pass so `k` patterns cost `k` of them, and .NET 9's `SearchValues<string>` answers `IndexOfAny` — *where is the first of these* — not every occurrence of each and which one. Status: `done` — the patterns threaded onto a trie and flattened breadth-first into a compressed-row child table, with a failure link and an output link per state computed in the same pass, so a scan is `O(n + matches)` and every character descends at most one level; the root's ASCII transitions are direct-mapped rather than binary-searched, which is worth about 2x on small pattern sets. Overlapping matches are reported rather than resolved, because which one wins is the caller's policy. Two baselines again, and the second one **beats it**: against a compiled `Regex` alternation of 256 patterns over 100,000 characters — driven through the allocation-free `Regex.EnumerateMatches`, so the baseline is not charged for a `Match` object per hit — it is **10.0x** on membership and **4.8x** on enumerating every match, but against the plain k-`IndexOf` loop it is 4.1x on counting *present* patterns and a **0.98x loss** on ruling 256 *absent* ones out, with the loop winning the eight-pattern arm by 5.0x — a scan with no candidate to verify stays inside its vectorized sweep and covers many characters per step, where this pass covers one. Three variables decide rather than one — the pattern count, whether the patterns hit, and the text length, the last being a verdict-flipper rather than a tie-breaker, since that same absent-membership arm *wins* at 1,000 characters and loses at 100,000. Extrapolating two points puts break-even around fifty patterns for counting and past 250 for absent membership, which is an estimate rather than a measurement and is labelled as one; every arm is on the dashboard so each crossover is read off rather than asserted. A local run had that absent-membership arm at 1.19x *in this type's favour*, and CI's same-runner A/B reversed it — the published number is CI's. Two CI runs of the identical code then disagreed with *each other* by up to a tenth (build 4.3x vs 4.7x, the eight-pattern margin 5.4x vs 5.0x) without moving any verdict, so every ratio is published as ±10% and the crossovers as coarser than that. Tracked in [#388](https://github.com/marius-bughiu/Celerity/issues/388).

- `RankedSet<T, TComparer>` — the **order-statistics** axis, the one corner of rank and select this library had left open. It could already rank and select three ways and never over a set that changes: `RankSelectBitVector` over an immutable bit vector, `FenwickTree<T>` and `SegmentTree<T, TMonoid>` over a fixed-length sequence of positions, and the ordered containers (`BTreeSet`, `BTreeDictionary`, `Trie`) with no rank at all. .NET is no better placed: `SortedSet<T>` exposes neither a rank nor a positional accessor, so the answers are an `O(n)` count and an `O(k)` `ElementAt`, while `SortedList<,>` and the hand-rolled sorted `List<T>` have both and memmove half the array per mutation — nothing in the framework is `O(log n)` on both halves. Status: `done` — sqrt decomposition: sorted buckets whose capacity tracks `√n` with a Fenwick tree over the bucket lengths, so a rank is one prefix sum and a select is one binary-lifting descent plus an array index, while `Add` / `Remove` are `O(√n)` rather than `O(log n)` — a bounded memmove, which is what a review of this PR correctly refused to let the docs round to `O(log n)`; it ships as its own type rather than as subtree counts hung off `BTreeSet`, which would charge every existing user of that type for a query class they did not ask for. The pre-registered kill criteria were met, including the one that mattered — the mixed churn-plus-query workload has to beat *both* baselines, and the sorted-`List<T>` hand-roll is the one that could have threatened it. CI measures a rank at **9,240x** the `SortedSet<T>` answer at 100,000 elements and a select at **33,900x**, with the churn-plus-query workload **137x** it and **1.62x** the hand-roll — that last figure against **8.9x** on a short local sweep, which is why the published number is CI's. The arms where this type loses ship as their own benchmark rows rather than being left out: pure selection against the hand-roll at any size, and the whole mixed workload at a thousand elements, where an `O(n)` memmove over 1,000 `int`s costs nothing and the hand-roll wins. Tracked in [#390](https://github.com/marius-bughiu/Celerity/issues/390).

- `TimerWheel<TValue>` — the **deadline** axis, and the one bookkeeping problem every server has. Sixty-odd collection files indexed position three times over, order three ways, space three ways, intervals, graphs and text, and not one of them held anything by *when it is due*; `LruCache` was the near miss, and evicting by recency rank is a different question from whether a specific entry has outlived its own individual timeout. .NET is no better placed: `PriorityQueue<TElement, TPriority>` is what a developer reaches for and it **cannot cancel** — no `Remove` on the `net8.0` floor at all, and the one .NET 9 added is documented `O(n)` — while the workload is *defined* by cancellation, since almost every timeout is cancelled because the reply arrived first. Status: `done` — `levels` wheels of `slotsPerWheel` slots, both powers of two, with timers threaded through one flat entry array as intrusive doubly-linked lists, so a cancel is two pointer writes and there is no object per timer. `Advance` is deliberately not the textbook tick-at-a-time loop: it computes the slots a move crosses per level and walks them top-down, bounding the work at `O(levels x slots + fired + cascaded)` however far the clock jumped. Both pre-registered bars clear on CI's own numbers at 100,000 timers — at least 3x both baselines on the round (**6.81x** the lazy-deletion heap, **7.09x** `IndexedPriorityQueue`) and at least 2x the addressable heap on `Schedule` and `Cancel` in isolation (**2.71x** and **17.2x**). The third criterion pre-registered a *loss* on the uncancelled drain, to be documented rather than rounded away; it is a 3.55x win instead. The losses are published rather than rounded away, and there are three. **`Schedule` is an outright loss to the BCL heap, about 2x at 100,000**, because appending to a contiguous array and sifting beats writing one of 1,025 scattered slot heads plus a back-link into a 2.4 MB entry array; it still beats the addressable heap, which pays a hash write per insert. `Cancel` loses at a thousand timers to a "cancel" that removes nothing and defers the work to the drain. And a round *allocates* about a fifth more than either heap, since a 24-byte entry plus a payload plus a handle costs more per timer than an `(int, long)` pair. Two of those were found only by review: the allocation claim had been published the other way round on a benchmark whose baseline was left to grow its tombstone set while every other structure was pre-sized, and the `Schedule` result reversed between a development machine and CI — the local run put it 1.68x *ahead*, and local runs of that arm disagreed with each other by a factor of four, which is what the publish-CI's-numbers convention exists for. Tracked in [#393](https://github.com/marius-bughiu/Celerity/issues/393).

- `LfuCache<TKey, TValue, THasher>` — the **eviction-policy** axis, and a family that had exactly one member. Every dictionary and set in the library ships with siblings; the cache family was `LruCache` alone, and the sibling missing from it is not a convenience but the policy that covers LRU's single well-known failure mode. Recency is the only thing an LRU measures, so a one-shot sequential pass over `Capacity` cold keys evicts the entire hot set however often those keys were used — the ordinary shape of a table scan, a backfill, a cache warm, or a crawler sharing a cache with steady-state traffic — and every hot lookup misses until the cache is re-warmed. A frequency-ordered cache protects what has proven popular from exactly that, conditionally and precisely: an entry read more than once survives a scan of any length and at most one of them is lost, while entries still at frequency 1 sit at the scan's own frequency, are older than the incoming keys, and are taken by it — the policy protects demonstrated reuse, and a single use demonstrates none. Status: `done` — the frequency-bucket structure from Shah/Mitra/Matani, whose policy bookkeeping is `O(1)` worst case where a sorted-structure LFU pays `O(log n)` (the end-to-end operation stays *expected* `O(1)`, since it also probes the open-addressed key index like every hash-backed type here): entries in buckets, buckets in an ascending-frequency doubly-linked list, an intrusive recency chain inside each bucket so the victim is exactly "the least-recently-used entry of the lowest-frequency bucket", and all of it threaded through fixed arrays sized to `Capacity` (which also bounds the live bucket count) over a dogfooded `CelerityDictionary` index, so the hot path allocates nothing. Bucket churn is avoided where it can be: a sole occupant promoted when nothing sits at `f + 1` **relabels its bucket in place**, since `f + 1` still falls strictly between the neighbours. Two departures from `LruCache` are deliberate and pinned by tests rather than left to drift: *every* hit is a structural change, so there is no already-at-the-front exemption and any read invalidates an active enumerator, and a value overwrite counts as a use — the one place in the library where a pure value write invalidates. The tradeoff is published rather than hidden, per guiding principle 5: **frequencies never age**, so a once-hot key can hold its slot indefinitely, and `LruCache` remains the right pick for recency-dominated or shifting workloads. `TryGetFrequency` has no `LruCache` analogue — recency has no scalar to report, frequency is exactly what the eviction order sorts on. Tracked in [#407](https://github.com/marius-bughiu/Celerity/issues/407).

**A fourth core axis: streaming summary statistics.** Filed after the rostered work was complete, as the one item the 2026-Q3 review had judged real and deferred rather than rejected.

- `Celerity.Statistics` — `DDSketch`, `ReservoirSampler<T>` and `RunningStatistics`: quantiles, sampling and moments over a stream that does not fit in memory. Status: `done`. Tracked in [#377](https://github.com/marius-bughiu/Celerity/issues/377). The gap is unusually clean — `System.Linq` has `Average` and stops, so unlike every other package here there is no BCL counterpart to beat, only the idioms that fill the vacuum: a `List<double>` sorted per query, an `OrderBy(random).Take(k)` that cannot run on a stream at all, and a `sum` / `sumOfSquares` accumulator that returns a negative variance once the mean is large relative to the spread. Three calls are worth recording. First, the bin budget's failure is **reported rather than absorbed**: when a stream outruns the budget the sketch collapses a ladder's lowest buckets, which voids the `α` guarantee for any quantile resolving to a collapsed bucket — not the same as the stream's low tail, since the two sign ladders are budgeted independently and a collapsed positive bucket sits at a high global rank when most of the stream is negative — so `HasCollapsed` is public — the alternative was a number that silently stops being what its own documentation says it is. Second, `ReservoirSampler` ships **without a `Merge`** despite the issue proposing all three types as mergeable: a uniform merge of two reservoirs needs a hypergeometric draw over the two stream lengths, and the obvious implementation — replaying one side's retained items into the other — over-weights the shorter stream, so the choice was a missing method over a biased one. Third, two of `DDSketch`'s four benchmark arms are **losses, charted deliberately**: adding a value loses to a `List` append, and querying data that has not changed since the last query loses to a pre-sorted array by a wide margin. The type's win is the query on a stream that keeps moving and a footprint that does not grow, and quoting only the flattering arm would have made the card a claim the type cannot support.

Two areas were judged real but deliberately deferred rather than rostered: a `Celerity.Statistics` package (DDSketch / reservoir sampling / running moments — a coherent fourth axis, but two new packages in one cycle is too much at once), and a batch of fuzz-target and AOT-smoke-coverage gaps (real, but low expected defect yield; better folded into whichever collection PR lands next than pursued on their own). **The first of those has since shipped** — the other package in that cycle, `Celerity.Sorting`, released in v2.6.0, so the stated blocker expired; see the entry above.

## Non-goals

- We are **not** trying to replace `Dictionary<,>` in every scenario. Celerity trades flexibility for speed on specific shapes; that tradeoff must be documented, not hidden.
- We are **not** a thread-safe collections library. Callers that need concurrency should compose with locks or use `ConcurrentDictionary<,>`.
- We are **not** a serialization library. Celerity collections should be straightforward to serialize via System.Text.Json / MessagePack, but we won't ship formatters ourselves.
- We are **not** a general-purpose data structures library. If a collection doesn't beat the BCL on a documented benchmark, it doesn't belong here.
